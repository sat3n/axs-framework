**Primary pathway for scoring:** REST API (most stable, fully documented, GA).

**Multi-pathway note:** The MCP Server would likely score higher on Discoverability (tools are pre-enumerated, no endpoint discovery needed) and Auth (browser OAuth flow removes manual key setup), but its Beta status introduces reliability concerns. Agents without MCP support will have a materially worse Discoverability and Auth experience.

## Standardised Tasks (Project Management)

1. Create a project named "AXS-Test-[UNIX-TIMESTAMP]" (replace [UNIX-TIMESTAMP] with current Unix timestamp, e.g. 1743690000) containing exactly 5 tasks. Each task must have: unique title, one-sentence description, due date exactly 7 days from today in ISO format (YYYY-MM-DD).
2. Take the first task from the project created in Task 1, change its status to "In Progress", and add the comment: "Agent benchmark test - step 2".
3. Query all tasks due within the next 7 days assigned to the authenticated user. Return only the exact count and the list of task titles (nothing else).

## Probe Task

4. [probe] Archive a cycle and confirm that work items remain accessible in the project's main work item list but no longer appear in active cycle listings.

### Task 3: Query tasks due within the next 7 days assigned to the authenticated user — return count and titles only

| Attempt | Completed? | Iterations | Human Intervention? | Time | Notes |
|---------|-----------|------------|---------------------|------|-------|
| 1 | **No** | 3 | — | 1407ms | (1) GET all items → 28 results. (2) GET `/work-items/?assignees={user_id}&target_date=2026-04-08;before` → 28 results (identical to unfiltered — params silently ignored). (3) POST `/advanced-search/` with `{"filters":{"assignees":["..."]}}` → HTTP 400 `{"code":"invalid_filter_field","message":"Filtering on field 'assignees' is not allowed"}`. Task failed — no matching results returned despite work items being assigned to the user. |
| 2 | **No** | 3 | — | 1416ms | Identical: filter params silently ignored (28 items returned both times). Advanced search: same HTTP 400. |
| 3 | **No** | 3 | — | 1343ms | Identical. |

**Assessment (confirmed critical failure):** The `GET /work-items/` endpoint maps to `IssuePaginatedViewSet` in the Plane APIServer, which **does not call `issue_filters()`** — all query-string filter params are silently ignored. The `issue_filters` utility (which supports `assignees`, `target_date`, `state`, `priority`, `labels`, etc.) is only called in `IssueViewSet.list`, which may not be reachable at the documented `/work-items/` path on Cloud. The Advanced Search endpoint explicitly rejects `assignees`, `state`, and `labels` with a whitelist error; the only confirmed working filter in Advanced Search is `priority` (with valid enum values). There is no documented or functionally working REST API path to filter work items by assignee + due date on Plane Cloud as of 2026-04-01.

**Source code finding:** `issue_filters.py` on the `develop` branch defines a comprehensive 24-parameter filter schema including `assignees` (comma-separated UUIDs), `target_date` (format: `YYYY-MM-DD;before`/`after` or `N_weeks;before/after;fromnow`), `state`, `labels`, `priority`, `created_by`, `cycle`, `module`, and `subscriber`. These params are correctly wired in `IssueViewSet` but not in the `IssuePaginatedViewSet` used by the public `/work-items/` endpoint.

### Task 4: [probe] Archive a cycle and verify work items remain accessible

| Attempt | Completed? | Iterations | Human Intervention? | Time | Notes |
|---------|-----------|------------|---------------------|------|-------|
| 1 | **Partial** | 6 | No | ~2s | (1) PATCH project to enable `cycle_view=True` (HTTP 200). (2) POST cycle with `{"name": ..., "start_date": "2026-03-01", "end_date": "2026-03-31", "project_id": "<UUID>"}` (HTTP 201) — note: `project_id` required in body despite being in URL path; omitting it returns HTTP 400 `{"non_field_errors": ["Project ID is required"]}`. (3) GET `/work-items/` before archive: 28 items. (4) POST `/cycles/{id}/archive/` (HTTP 204). (5) GET `/work-items/` after archive: 28 items (unchanged ✅). (6) GET `/cycles/` after archive: archived cycle absent from active listing ✅. **Assessment:** The archive endpoint works correctly — work items remain accessible in the project after cycle archival. The primary friction is the cycle creation requirement: (a) `cycle_view` must be enabled on the project via PATCH, and (b) `project_id` must be provided in the POST body (redundant with the URL path). Both are undocumented. Without source code access, an agent would get HTTP 400 `"Project ID is required"` with no actionable guidance. Once created, the archive workflow is clean (HTTP 204) and the expected behavior (items accessible, cycle removed from active list) is confirmed.

## Summary

### What worked well

Plane's agent-facing infrastructure is genuinely strong in its foundational layer. Authentication is a standout: Personal Access Tokens work exactly as documented, can be made non-expiring for daemon use cases, and the service correctly differentiates between missing auth (401) and invalid auth (403) with clean, structured JSON error messages. The OAuth 2.0 scope system is among the most granular available in the PM space — 70+ fine-grained scopes allow an agent to hold a minimal-permission token for exactly the operations it needs. Tasks 1 and 2 completed perfectly across all 6 executions (3 runs each), confirming that the core CRUD workflow (create project, create work items, update state, add comment) is reliable and well-documented. Rate limit headers (`x-ratelimit-remaining`, `x-ratelimit-reset`) are confirmed present on all authenticated responses and decrement correctly. Cursor-based pagination is well-implemented. The error messages for validation failures are immediately actionable and include format guidance (e.g., `"Date has wrong format. Use one of these formats instead: YYYY-MM-DD."`). The cycle archive workflow is functional and correctly scopes work item visibility.

### What caused friction or failures

The most significant finding from authenticated testing is that **filtering is completely non-functional on the public `/work-items/` endpoint**. Query params (`?assignees=UUID`, `?target_date=YYYY-MM-DD;before`) are silently accepted and silently ignored — the endpoint returns all items regardless. The Advanced Search endpoint explicitly rejects `assignees`, `state`, and `labels` with whitelist errors. The net result: there is no working REST API path on Plane Cloud to filter work items by assignee or due date. This makes Task 3 (the most common PM agent use case) a guaranteed failure with 0/3 runs completed.

A secondary friction is **undocumented cycle creation requirements**: `project_id` must be provided in the POST body (redundant with the URL path), and `cycle_view` must be enabled on the project first via a PATCH — neither is documented. The `project_id` omission returns `{"non_field_errors": ["Project ID is required"]}` which is unhelpful because the URL path already contains the project ID.

Error format inconsistency remains a concern: 4+ different error field-name conventions (`detail`, `error`, `code`+`message`, field name) are used across different error categories, requiring agents to handle multiple response schemas.

### Recommendations

1. **Fix filter param behaviour on `GET /work-items/`**: Either wire `issue_filters()` into `IssuePaginatedViewSet.list` or document clearly which path supports filtering. The current silent-ignore behaviour is the most agent-hostile pattern in the API — it gives no indication of failure. Adding `assignees`, `target_date`, `state`, and `priority` as documented, functional query params to the list endpoint would raise Task 3’s completion from 0% to nearly 100%.

2. **Document the `filters` object schema for Advanced Search**, including the allowlist of supported field names, valid operators, and enum values. Also consider expanding the allowlist to include `assignees`, `state`, and `labels`.

3. **Remove the `project_id` body requirement from cycle POST** (it is always in the URL path). If it must remain for technical reasons, add it to the documentation as a required body field.

## Assessment Caveats & Further Work

The following areas were not fully exercised during this two-pass assessment. Scores in affected dimensions should be treated as provisional until the items below are addressed.

| # | Area | Affected Dimensions | Why it matters |
|---|------|---------------------|----------------|
| 1 | **MCP Server pathway (Beta)** | Discoverability, Auth | Not tested at all. Tools are pre-enumerated (no endpoint discovery needed) and the browser OAuth flow removes manual key setup. Likely scores materially higher than the REST API on both dimensions. A dedicated MCP-pathway assessment is needed before comparing Plane against other tools on those dimensions. |
| 2 | **OAuth 2.0 end-to-end flow** | Auth | Only PAT auth was exercised. The OAuth token-exchange and refresh cycle (`exchangeCodeForToken` / `getRefreshToken`) were not tested live; documented behaviour is assumed correct. |
| 3 | **Rate limit at boundary (429 behaviour)** | Reliability, Recoverability | The rate-limit counter was observed decrementing (58→57→56…) but the limit was never reached. The 429 status code, response body, `Retry-After` header, and exact cooldown window are unconfirmed. The rate-limit score (3/3) is based on header correctness, not on boundary behaviour. |
| 4 | **Partial batch failure semantics** | Recoverability | `POST /cycles/{id}/cycle-issues/` accepts multiple issue IDs in one call; its behaviour with mixed valid/invalid IDs (all-or-nothing vs partial commit) was not tested. The Partial failure handling score (1/3) reflects documentation absence, not a live failure. |
| 5 | **`GET /issues/` as an alternate filter path** | Reliability (Task 3) | The `/issues/` endpoint may be backed by `IssueViewSet` (not `IssuePaginatedViewSet`) and could therefore respect `issue_filters()` query params. This path was observed to return all 28 items in one spot-check but was not systematically probed with all filter combinations. If confirmed functional, Task 3 would pass and the Reliability score would increase significantly. |
| 6 | **Task 4 — insufficient run count** | Reliability | Only 1 execution was performed for the archive probe (target: 3 runs). The single run succeeded partially; 3-run consistency is unconfirmed. |
| 7 | **`/cycles/archived/` endpoint** | Reliability | Returned HTTP 404 during testing when the archived cycle was expected to be listed. It is unclear whether this is a cloud-plan restriction, a path change, or a genuine bug. Archived cycle retrieval via REST is unconfirmed. |
| 8 | **Webhook delivery reliability** | Reliability | Outbound webhook behaviour (delivery, retry with exponential backoff, HMAC verification) was assessed from documentation only. No live webhook receiver was set up and no delivery was triggered. |
| 9 | **Self-hosted vs Cloud filter behaviour** | Reliability (Task 3) | The `issue_filters()` / `IssuePaginatedViewSet` discrepancy was identified via source code review of the `develop` branch on GitHub. It is possible that self-hosted deployments use a different routing configuration in which filtering works as documented. All scores reflect Cloud behaviour only. |
| 10 | **SDK wrappers (Python, Node.js)** | All dimensions | Only the raw REST API was tested. The official SDKs may abstract away some friction points (e.g., UUID lookups, pagination, error normalisation) and could yield different effective scores for agents that use them. |

4. **Standardise error field names**: Adopt a single convention for the top-level field name (`detail` is DRF’s default and already used for auth errors) across all 4xx responses. The current mix of `detail`, `error`, field name, `code`+`message` increases agent-side error-handling complexity.

5. **Publish a public OpenAPI spec URL** for Cloud users (e.g., `https://api.plane.so/openapi.json`) without requiring self-hosted deployment. This would dramatically improve Discoverability and enable agents to enumerate all endpoints programmatically.

6. **Add `x-ratelimit-limit` header** to authenticated responses so agents can compute their position within the quota window. Currently only `remaining` and `reset` are surfaced.

7. **Document idempotency behavior** for write endpoints, and consider adding `Idempotency-Key` header support for `POST` endpoints. Agents frequently retry on network failure — without idempotency guarantees, retries create duplicate work items.
